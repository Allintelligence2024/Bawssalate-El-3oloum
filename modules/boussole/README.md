# البوصلة | Laboratoire embarqué dans Boussole Lite

Dans la barre du bas, **البوصلة** lance directement le laboratoire de la même origine. « تمارين المنهجية الأخرى » donne accès aux ateliers conservés. L'aide du parcours de l'unité 1 ouvre un exemple de **protéines** dans un dialogue, précise qu'il ne résout pas l'exercice, et revient à la zone, la réponse et le focus d'origine. L'accueil présente les repères فعل ← دليل ← جواب ← فحص ; trois pages proposent des critères d'auto-relecture facultatifs, sans score ni correction automatique. La comparaison reste accessible à qui travaille sur papier.

Le laboratoire ne lit pas le compte Lite et ne met à jour ni `kafaa`, ni SM-2, ni statistiques. L'application conserve ses règles de connexion, mais `/boussole/index.html` est également accessible **sans profil** à la même origine. Les états d'exploration sont en mémoire et repartent à zéro quand le laboratoire est démonté ou rechargé ; seuls les textes du carnet sont persistés si le stockage fonctionne.

## Carnet, sauvegarde et suppression

- Le carnet courant est dans `localStorage["boussole.bac.classe16.carnet.1"]`. Il est partagé par les documents de la même origine, **non protégé par le compte**, et ne disparaît pas à la déconnexion. Ne pas saisir de données personnelles sur un appareil partagé ; supprimer les brouillons avant de le remettre.
- Le JSON de « أنا » inclut ce carnet en clair, sans compte, jeton ni consentement, dans `carnetBoussole`. Un champ `null` signifie qu'il n'y avait pas de carnet : le restaurer efface le carnet courant. Un ancien fichier **sans** ce champ le laisse intact. Tout carnet invalide fait rejeter le fichier avant écriture. Si la progression, le carnet local ou les statistiques sont illisibles, l'export complet est refusé plutôt que de présenter un état de secours comme une copie complète ; si le JSON dépasse 5 Mio ou ne respecte pas le schéma d'import, l'export est également refusé.
- Une restauration validée engage état, statistiques et carnet présents dans un journal ; en cas de quota, elle tente de rétablir les anciennes valeurs. Si ce retour échoue, le journal reste pour un rejeu au prochain chargement. Un journal illisible ou inconnu est conservé : un écran de reprise bloque les écritures et propose, seulement après avertissement et confirmation, de l'abandonner sans supprimer les autres clés. Cette opération peut laisser des données partielles ; garder le fichier de sauvegarde pour le réimporter si nécessaire.
- Lorsqu'un autre onglet récent modifie l'état ou les statistiques, ou engage une restauration, Lite suspend les écritures et les exports de l'onglet devenu périmé. Une comparaison des dernières valeurs lues est aussi effectuée avant les opérations sensibles et les nouveaux envois sync, sans attendre l'événement `storage`. Avant confirmation d'un import qui modifie le carnet ou d'une remise à zéro, Lite capture les octets du carnet et refuse l'opération s'ils ont changé ; la confirmation d'import est non bloquante. Le laboratoire compare le carnet avant écriture ou suppression et invalide une confirmation si un changement est reçu. Lorsqu'on demande de charger la copie enregistrée, un échec de lecture ou un journal en attente ne remplace pas la saisie temporaire par un carnet vierge. Si la valeur stockée devient illisible dans un autre onglet, le laboratoire conserve aussi la copie lisible déjà affichée pour permettre son téléchargement. L'écran de reprise permet de retourner copier ou télécharger cette saisie sans démonter son cadre. **Ce sont des contrôles optimistes, pas un verrou ni une transaction inter-onglets** : une écriture peut survenir entre la comparaison et l'opération, une valeur peut changer puis revenir à l'identique, les versions anciennes peuvent ignorer les protections et des requêtes déjà parties peuvent se terminer. Les modifications ne sont pas fusionnées : fermer les autres onglets avant import ou suppression.
- La réinitialisation de « أنا » supprime le journal avant l'état, les statistiques et le carnet courant ; elle signale un échec de suppression. Fermer les autres onglets avant de l'utiliser : un ancien onglet ou une ancienne version peut encore réécrire ses données. La déconnexion n'efface rien. Les **carnets d'anciennes versions** 1.4 ب et 1.5 sont exclus de la sauvegarde et de la réinitialisation ; les copies de fichiers téléchargés et les données serveur sont également hors de leur portée. Pour effacer les anciennes données du site, utiliser les réglages du navigateur après avoir sauvegardé ce que l'on veut garder. Un HTML ouvert depuis un autre fichier ou une autre origine a son propre stockage.
- La synchronisation éventuelle de Lite n'envoie pas ce carnet. Les nouveaux envois sont également suspendus si la progression ou les statistiques nécessaires sont illisibles ; le retrait du consentement peut être enregistré lorsque la progression reste lisible et cohérente, même si les statistiques ne le sont pas. Les exports JSON ou texte sont des copies explicites que leur propriétaire doit garder en lieu sûr.

## Construction et tests

À la racine, `npm ci && npm run build` utilise les fichiers versionnés dans `public/boussole/` et les inclut dans le manifeste hors ligne. Pour **modifier le laboratoire** : dans `modules/boussole`, exécuter `npm ci`, `npm run typecheck`, `npm run build`, puis rebâtir l'application depuis la racine. Le HTML autonome embarque ses ressources ; les deux PDF sont des fichiers distincts.

`npm test` dans ce dossier exécute la logique et les tests Playwright du HTML autonome, y compris les conflits et interruptions de stockage (`npx playwright install chromium` si nécessaire). Depuis la racine, `npm test` couvre notamment l'import, le carnet, le rejeu, le quota, les formats de compte, la réinitialisation et le contrôle d'inventaire ; `node scripts/verifier-hors-ligne.mjs` vérifie les ressources du build. `npm run verifier:inventaire-boussole` signale les fichiers manquants, nouveaux ou modifiés dans les deux répertoires inventoriés : il ne vérifie **ni les droits ni la qualité pédagogique**.

Pour tester l'intégration sur le build **local**, sans base distante :

```sh
# Terminal 1, à la racine du dépôt
npm run build
npm run preview -- --host 0.0.0.0 --port 4182

# Terminal 2
cd modules/boussole
APP_URL=http://127.0.0.1:4182 npm run test:integration
```

Les scénarios utilisent des profils fictifs locaux ; ne pas les pointer vers une instance publique. Ils couvrent aussi la reprise d'un brouillon temporaire lors d'un conflit entre onglets et la création/connexion/déconnexion d'un compte local avec ou sans WebCrypto. Le workflow CI prévoit ces suites, la reconstruction reproductible du HTML et le contrôle hors ligne. Il utilise Ubuntu 24.04 pour la compatibilité avec Playwright 1.56.1 ; consulter les contrôles GitHub Actions du commit testé pour son résultat. Le workflow ne déploie pas lui-même, mais l'intégration Vercel peut déployer automatiquement un push ou une fusion. Ne pas déployer ce dossier à la place de l'application.
